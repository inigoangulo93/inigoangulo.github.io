How to scope an MVP for AI agents: the one workflow rule and the list of what you will not build

Inigo AnguloNovember 4, 20267 min readBuilding with AI agents

Scoping an MVP for a human team is about effort: what can four people ship in a quarter. Scoping an MVP for AI agents is about bounds: what must the product never do, and what must always hold, because the effort constraint is gone and nothing else stops the build from sprawling. The scope document I use has four parts and fits on one page. The page took a week to write and it was the most valuable week of the build.

Part 1: the thesis, in one sentence

What can the user trust the product for? Not what it does; what it is for. Mine was: the user can trust a single record of their collection, knowing where each item is, what is happening to it, and who made each change. Every ticket for seven weeks was tested against that sentence. A feature that did not serve it was not built, however easy it was.

The thesis goes at the top of the project rules file, so every agent reads it in every session. It is also the sentence an agent uses when it escalates a decision: "this does or does not serve the thesis" is a question I can answer in seconds.

Part 2: one workflow, end to end

The MVP proves one workflow. For mine: a user adds an item with a photo, the model proposes the fields, the user confirms, the record exists with an audit trail. Screens, data model, permissions and the model call, for that workflow and nothing else.

The rule is not "one feature". A workflow is a path through the product that a customer would pay for on its own. What the rule forbids is the second path. With agents the second path feels free, because the code arrives in an afternoon. It is not free: every path multiplies the states that the tests, the browser suite and the penetration test have to cover, and those are the costs that do not compress.

Scoping for a teamScoping for agents
Bounded by effort: what fits in the quarterBounded by invariants: what must never break
Feature list, prioritisedOne workflow, plus a list of what is not built
Requirements in prose, clarified in meetingsRequirements as acceptance criteria an agent can test
Security as a phase near the endPermissions matrix written before the first screen
Decisions taken in conversationDecisions logged with an id, because sessions forget

Part 3: invariants, marked by where they are enforced

An invariant is something that holds in every state. Mine included: no proposal from the model writes to an entity, a person decides and the system records who; sensitive identifiers are encrypted before they reach the database and are never searchable; a user whose account is pending reads zero rows of any table; every business write leaves an audit entry.

Each invariant carries a mark: enforced in the database, enforced in the application, or both. The one place an invariant is never enforced is only the interface, because hiding a column in the frontend is not a guarantee and an agent will not know the difference unless told. This list becomes the permissions matrix, and the permissions matrix becomes the security tests. Writing it first means the tests exist before the screens do.

Part 4: what is not built

This is the part teams skip and the part that saves the most money with agents. Mine said, among other things: no search by sensitive identifier, no identity documents stored anywhere, no infrastructure for a hypothetical need, no second backend, no queue, no cache layer until a measurement justifies it. Each line has a reason.

The effect on the build was immediate. When an agent proposed a cache for a page that loaded in 80 milliseconds, the rules file already said no, with the reason, and the proposal cost one line of reply. Without that list the same proposal costs a conversation, and the tenth such conversation is where scope dies.

What the page produces

From this one page come three artefacts that the agents work from: the project rules file (thesis, stack, hard rules), the domain model with its invariants, and the permissions matrix. Tickets reference them instead of restating them. When something is not in one of the three, for an agent it does not exist, which is exactly the property you want: the scope is the documents, not the memory of a conversation.

This is step 1 of how to build an MVP with AI agents. Next: the project rules file, then tickets agents cannot misread. If you want the scoping done with you, that is the first week of an AI build sprint.

Questions people ask

How many features should an MVP built with AI agents have?

One workflow, end to end, that proves the thesis. Not one feature: a workflow has several screens and a data model. But one. Agents make adding a second workflow feel free, and it is not: every workflow multiplies the states the gates have to cover.

Why write what will not be built?

Because agents build what you do not forbid. A feature list bounds the human team by effort; it does not bound agents, for whom the marginal feature costs minutes. The not built list is the only bound that works.

What is an invariant in this context?

A statement that must hold in every state of the product, such as 'no proposal from the model writes to an entity; a person decides and the system records who'. Each one is marked with where it is enforced: the database, the application, or both. Never only the interface.
