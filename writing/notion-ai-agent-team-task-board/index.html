Notion for AI agent teams: the board is the control plane, the repo is the source of truth

Most guides to running AI agents from Notion stop at the satisfying part: a card moves to a column, an agent picks it up, a pull request appears, the card links to it. That part works, and Notion now ships it out of the box. It is also the easy half. The hard half is everything around it: where the agents get their instructions, who is allowed to write what on the board, how a decision taken on a card reaches the next session, and what Done means when nobody on the team wrote the code.

This is the coordination layer behind a production build I ran for a private client: one person, a team of AI agents, a board of more than four hundred cards and a client team working on the same board in legal, sales, brand, finance and operations. None of it is clever. It is a handful of rules about which system owns which truth.

Rule 1: the repo instructs, Notion remembers

An agent session starts by reading the repository: the project rules file (CLAUDE.md in Claude Code) and the documents it points to. That is the only thing guaranteed to be in its context every time. So the operational reference lives there and only there, and Notion is explicitly not allowed to become a second one. The sentence at the top of the workspace home says exactly that: the reference for the agents lives in the repo; Notion keeps the institutional context and the decisions; there is no second set of instructions competing with the repository.

The failure this prevents is slow and expensive. Someone writes a convention on a Notion page because it is quicker than a pull request. Two weeks later the repo says one thing, the page says another, and whichever the agent read last wins. With a single source of instructions that argument cannot start.

Rule 2: the orchestrator drafts, a person owns

Cards are drafted by the orchestrator agent, the one that decomposes work and never merges. It writes them the way it writes tickets, because that is what they are: the goal in two sentences, the scope as numbered steps, an explicit out of scope list, acceptance criteria an agent can prove, and the open decisions at the bottom. The ticket template and the card are the same document in two places, and the card's number is the repo's ticket number, so there is never a question of which one is meant.

What the orchestrator never fills in is the owner. The owner field is always a real person in the workspace, never a name typed as a tag and never an agent. The owner is who answers when the card is blocked, who decides its open questions and who is accountable for what ships. An agent can do the work; it cannot be accountable for it.

The last two sections are the part I would keep if I could keep only one. The orchestrator is allowed to take technical decisions that change nothing a user or a role would notice, and it writes them down under its own heading. Everything else goes up as a numbered decision with three options and a recommendation, and the answer is written on the card, by the owner, as an id and a letter. The lead agent then records it in the repo's decisions log, citing the id. One decision, one id, findable from both sides. The format is in the kit as the escalation format.

Rule 3: Done means merged and passed

The board's states are ordinary: backlog, to do, in progress, blocked, done, archived. What is not ordinary is the definition of the last real one. The rule on the workspace home is one line: nothing is marked done without a merged pull request and a PASS from the reviewer. The card links to the pull request, the pull request carries the evidence (the run ids, the test counts, the screenshots), and the board only reflects that the evidence exists.

That keeps two vocabularies apart on purpose. The board tracks work: is it queued, moving, stuck, closed. The repo tracks proof, in stricter words (VERIFIED, IMPLEMENTED, NEEDS_REVIEW, BLOCKED, DECISION_REQUIRED) that an agent has to back with something a script produced. A card that moves to Done because an agent said "done" is a status, not a fact, and the whole point of the gates is that statuses are not facts.

One more rule from the team's working agreement saves a surprising amount of confusion: a closed card is never reopened. If something comes back, a new card is created and linked. The history of the old one stays true.

Rule 4: one board for the whole business, not only the code

The board is not an engineering board. The same database carries cards for product and tech, legal and import, sales and growth, brand, company and finance, and operations. That sounds like a detail and it changes the conversation: a legal blocker and a migration show up in the same weekly walk, with the same fields, and a product decision that depends on a pricing decision cannot quietly wait for it.

The working agreement that makes this hold is short. Every card has an owner, an area and an expected result; without an expected result it does not move to next. At most three cards in progress per person. A blocked card is raised in chat the moment it blocks, not at the meeting. The weekly meeting is thirty minutes: walk the board person by person, record decisions, move cards, nothing else, and everyone updates their own cards before it, not during. A decision that is not in the Decisions database does not exist.

What I would not hand to an agent

  • Moving a card to Done. It follows the merge and the review, not a message.
  • The owner field. Always a person.
  • Answers to open decisions. The agent recommends; the owner writes the letter.
  • Instructions. If an agent needs to know it, it goes in the repo through a pull request, where it is reviewed and versioned.

Everything else, drafting the card, keeping the scope and criteria in shape, linking the pull request, writing down its own technical calls, is exactly the kind of tedious, structured writing agents are good at. That is the division: the agents keep the board honest and complete; the people keep it accountable.

Questions people ask

Should the agents read their instructions from Notion?

No. Agents read the repository at the start of every session, so the rules file and the docs there are the only instructions that exist for them. Notion holds context, decisions and the work queue. A second set of instructions in Notion will eventually contradict the repo, and the agent will follow whichever it read last.

Can an AI agent own a task on the board?

It can draft the card and do the work, but the owner field should always be a real person. The owner is who answers when the card is blocked, who decides the open questions and who is accountable for the outcome. An agent cannot be accountable.

What does Done mean when agents do the work?

Done means the pull request linked from the card is merged and the reviewer said PASS on it. A card that moves to Done on an agent's say so is a status, not a fact. If something comes back, the card stays closed and a new one is opened, so the history stays readable.

Do I need Notion's own agents for this?

No. Notion now ships agents that pick up a card when it moves to a column, which is useful for small, self contained tasks. The structure in this article works with any agent that can read and write the board through the API or MCP. The value is in who may write what, not in which agent does it.
